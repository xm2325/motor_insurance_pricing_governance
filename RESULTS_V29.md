## What the attestation adds

The v0.27 lock answers: **are these the same sealed files that this bundle claims to contain?**

The v0.29 GitHub artifact attestation adds a separate question: **can the release archive be cryptographically linked to the GitHub repository/workflow/commit that built it?**

The attestation was generated by `actions/attest` using GitHub Actions OIDC and Sigstore-backed verification material. The persisted `gh attestation verify` result binds the attested subject to this repository, the v0.29 workflow, the feature-branch ref and the build commit.

## Packaging boundary

The attested subject is the **release archive**, not the raw training dataset. Before attestation the workflow checks that the archive contains the sealed manifest/lock/parity reference and does not contain the 94.7 MB raw Mendeley portfolio data.

The archive is assembled deterministically (`tar --sort=name`, fixed mtime/ownership, `gzip -n`) so packaging noise is reduced; the attestation nevertheless always applies to the exact SHA-256 subject generated in that run.

## Interpretation boundary

GitHub artifact attestations provide cryptographically verifiable **build provenance and subject integrity**, not a guarantee that an artifact is safe, statistically valid or suitable for production. The attestation does not approve XGBoost for customer pricing, does not replace the v0.20 model-governance HOLD decision, and does not establish transfer to FIRST CENTRAL or the UK motor market.

The attestation also does not make the underlying workflow automatically trustworthy: consumers still need to inspect and apply policy to the repository, workflow, commit and build instructions referenced by the attestation.
